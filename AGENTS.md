# Architecture rules

- Campaign cycle folders store reviewed years once per root in separate metadata; descendants inherit their root folder so classification never changes campaign content or cloning behavior.

- Performance changes preserve complete exact-count pagination, live invalidation and eager shared quantity availability; optimize query indexes and independent request scheduling instead of disabling data needed by existing actions.

- Loja a Loja letter copying uses a dedicated iterative dialog and pure row builder; new rows omit source IDs, share image references, and read fresh destination order before each insertion to keep copies independent.

- Rateio review keeps capacity matching and findings in one read-only pure engine shared by the dialog and PDF; client field labels are passed from Rateio so capacities do not depend on fixed custom-field indices.
- Rateio review kit checks derive kit counts only from components exclusive to one kit and add new finding types through FINDING_TYPE_LABELS, which the dialog and PDF iterate, so shared pieces are validated as the sum of their kits.
- Rateio kit_incompleto skips expected absences only via deterministic rules (opposite era, or piece zeroed in ≥90% of kit-receiving stores with base ≥4) when every missing component is zeroed; grouped kit findings fingerprint the sorted store set so a new affected store reopens a justified finding.

- Matrix quantity prefill reuses Flow name tokens and shared pure matching/filter helpers; reread paginated current quantities before confirmation so existing positive cells are preserved without changing the parent importer.
- Matrix prefill uses one unified transfer (sourceQuantityPerStore + applyQuantityToTarget) for any source→target type combination: kits count as min floor of component qty ÷ qty-per-kit, kit targets expand to each component × qty-per-kit; kit components are never mapped individually, so differing kit structures stay consistent.
- Renegotiation "vigente" campaign is the chain leaf (no other campaign of the client has parent_campaign_id pointing at it); import-source pickers show leaves only, so originals and intermediates can never be picked.

- Flow creation uses a shared record builder for kit/component payloads and one code/order counter; kit naming is shared with New Kit to prevent convention drift.

- Individual team exports use a shared labeled-field model for Excel and both clipboard formats so installer documents and vehicle details stay consistent.
- Copy team details as HTML plus plain text, falling back to plain text when rich clipboard is unavailable, because destination applications support different formatting.
- Team duplication reads fresh source records, preserves all member/vehicle fields and support coverage, and removes incomplete copies on failure; original teams and schedule assignments stay untouched.
- Loja a Loja overdue KPIs, drill-downs, and list/card highlights use one shared predicate honoring configured status closure and local-day deadlines, so visual counts stay consistent.
- Execution imports use one transactional, permission-checked RPC with same-client validation, name-based team remapping and skip-existing schedules; copied media rows share immutable files, so deletion must check all references before removing storage objects.- Rateio review justifications are stored per client by normalized fingerprint built only in the pure rateioReviewJust module (type+item+store/model, type+item for all stores; vitrine findings use subtype+store, or their situacao signature for all stores, while still honoring legacy subtype-less fingerprints) and filtered by one splitByJust shared by screen, Reanalisar and PDF, so the detection engine stays pure and justifications carry across campaigns of the same client.
- Bulk occurrence status changes go through one SECURITY DEFINER RPC that rechecks admin/master role, campaign access and the client's configured statuses, because table RLS alone lets any campaign editor update rows.
- Loja a Loja Classificação lists every store that physically receives pieces (install or freight-only) via one shared predicate; only 'sem_logistica' is hidden, so freight-only stores like kiosks stay classifiable.
- Superseded renegotiation campaigns redirect to the chain's newest campaign unless the URL carries the explicit-version marker and the user can load that version, so deliberate "view original" clicks work while old links still land on the current one.
- Supplier change markers in renegotiations are manual rows per piece/kit (removed items store code/name snapshots); portal reads them through a token-scoped SECURITY DEFINER RPC, and portal, Excel and invitation texts share one pure wording/counting module so suppliers see identical information everywhere.
- Manual piece/kit code edits share one pure conflict check (pieces and kits share a campaign numbering space) plus a fresh database recheck before saving; repeated codes warn and require confirmation instead of being silently accepted.
- Yes/No custom store fields are read through one tolerant parser (isCustomFieldTrue) accepting spreadsheet variants like TRUE/Sim/1, while saves always write lowercase true/false, so imported values never display as "Não".
- Tratativa status access (admin-only visibility and fallback forwarding for non admin/master saves) lives in one pure module (tratativaStatusAccess) used by the status manager and occurrence detail, mirrored by a BEFORE UPDATE trigger that converts (never rejects) non admin/master writes; new columns default off so existing statuses keep behaving unchanged.
- Occurrence material/reinstallation timeline state (steps, headline, tone, next step) comes only from the pure tratativaTimeline module shared by the internal sheet and store portal, mirrored by the status-board RPC counters; date-only columns are compared as strings to avoid timezone drift, and step authors are stamped by a DB trigger, never sent by the client.
- Supplier-portal price-history snapshots are built server-side by the token-validated supplier_portal_snapshot RPC, because anonymous visitors cannot read budget prices or extra costs; authenticated screens keep the client-side snapshot helper.
- Occurrence WhatsApp replies are built only by the pure occurrenceWhatsappMessage module (date-only strings formatted without new Date, empty lines omitted) and sent by the user via wa.me; the dialog never writes data except generating the store portal token on explicit click.
- Every list of round participants (send-to-client dialog, comparison export, cost analysis, Rateio requote picker, supplier campaign history) excludes consulted_only suppliers, because they keep a copied "enviado" status from the previous round.
- Insert-notification triggers for occurrences and installation photos skip rows whose created_at is older than 10 minutes, because renegotiation clones copy rows with their original timestamps and must not fire per-row alerts.
- Agendamento, Instalações, Loja a Loja and Ocorrências open only on the chain's newest campaign: LATEST_ONLY_SECTIONS and latestOnlySectionState in campaignVersionLink decide wait/redirect/stay (SPA navigate with notice, version marker dropped), because field-operation data lives only on the current version; other modules keep honoring the explicit-version marker.
- clone_campaign_for_renegotiation clones commercial data (pieces, kits, rateio, quotes, mockups) but moves field-operation rows (Loja a Loja, schedules, installations, occurrences, portal links) by updating campaign_id with ids kept, only from the chain's newest campaign; screens that summarize field data on an older version read from the latest campaign.
- Pending-installation counts (campaign Resumo card, status panel, home KPI) use isVisiblePendingInstallation (open, store with logistics, date+time) read from the chain's newest campaign via fetchPendingInstallationsCount/latestCampaignIdsByChain, so every screen matches the Installations list.
- The Rateio review store card (StoreFichaDialog) is read-only and built only from data already loaded by the dialog through the pure storeFicha module; kit counts reuse sourceQuantityPerStore so the card matches the Rateio kit rule.
- Rateio review "fill missing" builds writes only in the pure rateioFillMissing module and saves through the Rateio's applyWithHistory passed as a prop (editors of the current version only), so changes enter undo history; it takes one quantity per store (suggested from same-showcase-count stores), never deletes or lowers quantities, and shared kit pieces add to existing amounts.
- Rateio review item codes render only through itemCodeLabel (reviewRateio.ts), shared by dialog and PDF; multi-item (vitrine) findings show no code.
- Rateio review display helpers live in pure modules rateioReviewView, rateioItemDetail and storeFicha.findingConcernsStore; filters never feed the PDF or top counters.
- Rateio review per-store labels come only from storeSuffixes/storeQtyLine/withQuantities in reviewRateio.ts, shared by dialog and PDF; storesInfo/storeItemQty are display-only and never feed fingerprints, justifications or the fill-missing button (which still relies on storesWithQty/storesWithoutIds).
- Rateio review store names become ficha links only through StoreNameLink (lookup by name or nickname) and LinkifiedText over the pure storeNameLinks splitter (longest name first, accent/case-insensitive, word boundaries); the ficha dialog carries data-store-ficha so popovers underneath stay open, keeping one linking rule for every list and text.
- Rateio review store-card editing turns per-item drafts into cell writes only in the pure rateioStoreEdit module (shared pieces = sum of the store's kits) and saves through the Rateio's applyWithHistory passed as a prop (same permission as fill-missing), so edits enter undo history and respect the active rateio source.
- Rateio review store notes are display-only, derived only in the pure storeNotes module (shared by StoreNameLink showNote and the PDF) and never feed detection, fingerprints or justifications.
